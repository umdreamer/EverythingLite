# 开发流程规范

本规范适用于 Everything Lite 此后的产品开发、修复和流程维护。已发布的历史提交与标签不按新规则改写。具体构建命令见[开发指南](DEVELOPMENT.md)，贡献和隐私要求见[贡献指南](../CONTRIBUTING.md)。

## 1. 需求与版本

开发前把每项需求归为架构、功能或 Bug，并与维护者确认目标版本。混合需求拆开处理，先完成 Bug 修复，再开发新增功能，最后安排重大架构变更。不要把不同类别塞进一条 Issue 或一个提交。

版本采用 `x.y.z`：重大架构变化使 `x` 加一，并把 `y.z` 置零；新增功能使 `y` 加一，并把 `z` 置零；只有 Bug 修复时使 `z` 加一。每次决定版本前核对当前源码、标签与已规划分支。只改文档、测试基础设施或开发流程且不改变应用行为时，先确认无需增加应用版本号。

## 2. Issue、分支与提交

层级为一条目标版本分支包含一条或多条同版本 Issue，每条 Issue 包含一条或多条提交。一个提交只能关联一条 Issue；不得把多条 Issue 的修改合在一个提交中。提交应是可以独立审查、验证和回退的最小完整改动，不拆成无法构建或无法验证的半成品。

每个 Bug、功能或架构任务单独建立 GitHub Issue。Issue 写明类别、目标版本、现状或需求、预期结果、具体修复或实现方案、验收条件和测试计划。开始实现前，在 Issue 中说明实施步骤；建立分支后附上分支链接。没有真实 Issue 编号时，可以继续只读分析和写本地草稿，但不得编造编号，也不得创建需要关联 Issue 的提交。

产品版本从最新 `main` 创建 `release/vX.Y.Z` 分支；只改流程且经确认不升应用版本时，使用 `process/issue-N-主题` 分支。工作前检查当前分支和未提交改动，避免夹带别的 Issue。开发期间每次提交写清该步骤的改动和测试结果，使用真实提交时间及仓库允许公开的作者身份。

## 3. 三级测试门槛

**提交级：**先运行与本次改动对应的测试用例，再提交。测试须覆盖该步骤的行为或文档检查；记录实际命令和通过结果。任何相关测试失败时，先修复并重跑，不能提交。提交信息只引用一条 Issue，并使用 `Tests:` 和 `Test-Result: PASS` 记录证据；未运行的命令不能写成已通过。仓库的 [commit-msg Hook](../.githooks/commit-msg) 和[检查脚本](../scripts/check_commit_policy.py)只检查提交消息格式，不能代替实际执行测试。首次使用本仓库时运行 `git config core.hooksPath .githooks`。

**Issue 级：**完成该 Issue 全部验收条件及必要回归，把测试用例、命令、结果和未验证范围写在 Issue 评论中。相关测试失败时，Issue 不能记为完成。Issue 经分支合并、远端核验后再关闭，确保关闭状态对应已交付内容。

**分支级：**全部 Issue 的验收测试通过后，运行目标平台适用的完整 Debug 构建、测试及必要的打包和人工交互检查。记录命令、结果、测试数量及未验证范围；自动测试不能替代未做的手工验证。分支级检查失败时，不合并、不打标签、不发布。

```text
fix(mac): preserve selected result (refs #123)

Tests: QT_QPA_PLATFORM=offscreen ctest --test-dir build/gui-debug -R '^ui$' --output-on-failure
Test-Result: PASS
```

## 4. 合并、标签与发布

合并前检查分支只包含目标版本的 Issue、每个提交只关联一条 Issue，且工作区和暂存区没有无关改动。如果 `main` 在开发期间前进，更新分支并重跑受影响的测试。所有验收通过后，快进合并到 `main`，保留原始提交；不得把多条 Issue 压成一条提交。推送并核对远端 `main` 后，按目标版本创建标签或 Release，记录每条 Issue 的交付结果，最后删除已合并的远端和本地分支。

纯 Bug 修复版本推送版本标签，不为每个修复版本单独创建 GitHub Release。每累计五个纯修复版本标签，创建一次维护 Release；计数从上一次维护 Release 后开始。新增功能版本创建 Release。重大架构版本的发布内容在目标版本确认时单独确定。流程或文档变更若不升应用版本，不创建应用版本标签或 Release。既有标签不得移动。

发布前同步源码版本、README、CHANGELOG 和适用的打包标签。只有实际完成并核验的构建、测试、人工检查与分发检查才可写入发布说明。公开 Issue、提交、日志或截图前检查个人路径、搜索词、邮箱及其他敏感内容。

## 5. 完成记录

每个提交保留一条 Issue 引用和提交前的测试证据；每条 Issue 评论保留方案、验收结果及对应提交；分支合并记录保留完整测试结果、远端 `main` 的提交号、标签或 Release 状态，以及分支删除结果。无法完成任一门槛时，明确记录阻碍和未完成项，不宣称完成。
